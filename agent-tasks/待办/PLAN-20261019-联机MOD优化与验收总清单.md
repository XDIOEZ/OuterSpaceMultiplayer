### P0-1：先明确“执行、应用、保存”三个不同承诺

**生产证据：** `src/Session/Commands.cs::ExecuteOnSimulator` 已在成功回执前调用 `PublishLocalMaps`，但 `AcceptExecution` 随后仅核对 pending、模拟者和任期，便删除 pending、写入 `World.Transactions`，未验证本命令对应的地图 `CommitId` 是否已被 `AcceptMapUpdate` 接受。`src/Session/Authority.cs` 的地图 ACK 有 `SessionId/CommitId/MapId/AuthorityEpoch/BaseRevision/Revision`，可以作为关联设计的已有基础，而非另造一个独立全量地图机制。

- [ ] **契约评审（Session Owner 主导）**：为每条远程命令确定跨重新投递稳定的 `PlayerId + CommandId` 身份，并记录房间 `SessionId`、`MapId`、`AuthorityEpoch`、执行结果及能证明业务变化的地图事务/水位。先判断现有 `CommandResult` 是否足以携带证明，再评审协议兼容；**禁止仅靠“发送在前”判断主机已应用**。
- [ ] **状态机设计**：`Queued → NativeExecuted → AwaitingMapCommit → HostApplied → HostSaved（关键事务）`；拒绝、超时、任期变化及 native 不确定状态使用独立受控终态。`HostApplied` 与 `HostSaved` 必须有不同回执；非关键普通进度可回退最近完整 `SaveGeneration`，关键资产必须保存后报最终成功。
- [ ] **两种合法结果分别处理**：确实产生地图/个人差量的指令要等待关联提交；**未产生地图差量**但原生成功的操作，必须有房主可核对的明确无变化证明/业务结果，不可无期限等待，也不能把“没看到差量”当作已提交。
- [ ] **失败原子性**：地图拒绝或旧任期时，不应把成功 `Applied=true` 写入最终事务；同一 `CommandId` 重放不能再次执行已发生的原生副作用。若无法证明原生副作用是否已发生，应冻结并要求恢复，而非自动重试发奖/扣款。
- [ ] **故障注入**：地图先到/`execution` 先到、重复/乱序 ACK、队列满、权威切换、断线重连、SaveOrThrow 失败、最后完整代恢复、命令执行成功但无地图差量；逐例断言一条命令最多一次真实扣发，最终回执不早于应有提交。
- **依赖与交付**：[BUG-01](BUG-01-远程地图提交时序.md) 主卡、BUG-02 的回执索引、BUG-08 广播隔离、BUG-10 退出检查点需统一签收；提供状态转移表、关联字段契约、生产调用链链接测试、双端日志，**禁止修改 `Commands.cs/Authority.cs` 的其它 Owner 脏 hunk**。

### P0-2：区分“能提交此图”与“能修改此人”

**生产证据：** `src/Session/Authority.cs::AcceptMapUpdate` 已验证地图模拟者/任期、UID 来源、`PlayerUpdate` 所属玩家是否在图上，以及个人 `BaseRevision/Revision` 连续性。这些是必要条件，但**无法证明更改他人资金、科技、任务的业务原因**。`AcceptPersonalUpdate` 对单独个人包要求 `sender == update.PlayerId`（房主例外），两条路径不能混为一谈。

- [ ] **先由 Game Owner 分类字段**：① 地图合作自然产生的可归属资源/携带物品；② 仅本人指令或房主权威才能改的资金、科技、任务；③ 合法跨玩家运输/奖励等必须带原始 `TransferId/CommandId` 的关联变化。每个字段要注明原版触发入口、持久化位置及是否允许模拟者代理。
- [ ] **设计可验证来源**：房主对每组个人变更确认请求者、场景、所属地图、访问关系、前态/后态、已确认事件与一次性结算键；**先整组鉴权再进行任意 native map/personal 写入**。访客的正常劳动、任务背包及随身物品不得被简单归零或全拒绝。
- [ ] **负向回归**：模拟者替访客增加资金/科技、伪造任务完成、旧 `PersonalRevision`、旧 `AuthorityEpoch`、错误玩家映射、同事务重复 `PlayerId` 均须无副作用拒绝；正向回归包括房主本人、访客正常工作、随身携物、运输单真实交割。

### P0-3：身份安全先定威胁模型，不能只换哈希函数

**生产证据：** `src/Core/Storage.cs::CryptoData.Proof` 以 `Verifier` 的 Base64 字节充当 HMAC 密钥；`src/Session/Networking.cs::AuthenticatePeer` 使用房主保存的 `CredentialHash` 验证该证明，`src/Session/Credentials.cs::RecoveryCode` 也包含 `Verifier`。因此持有 verifier 的一方能构造后续挑战证明。是否将房主视为可信，需要明确产品约束。

- [ ] **威胁模型评审**：区分意外泄漏/第三方窃听、恶意房主、房主主动篡改其世界存档、凭证跨世界复用四类情况；明确哪些能由 MOD 解决，哪些因房主掌握世界数据而**无法保证**。必须明确 TCP 未加密链路的保护方式。
- [ ] **候选方案比选**：优先评估“客户端持私钥、房主仅存公钥”的挑战签名模式，消息签名覆盖 `WorldId/SessionId/CredentialId/Nonce/协议版本`；选型前核对实际 Unity/Steam/TapTap 的加密 API 与分发兼容性。仅以 HMAC 叠加盐或再次哈希 **不解决校验方拥有等效密钥** 的问题。
- [ ] **旧档与恢复迁移**：定义旧验证值安全升级的首次绑定策略、旧恢复码失效/换发、凭证丢失时房主显式重绑、同 `PlayerId` 资产原位保留、撤销旧身份的原子保存。不得凭昵称/IP 自动合并。
- [ ] **负向/正向回归**：仅持 verifier、捕获旧挑战、换 WorldId 重放、重连/并发同身份、跨 Steam/TCP 绑定、回滚最后完整档与取消迁移；验证拒绝冒用、合法恢复、不重复初始资产且不把秘密写进日志。
- **依赖与交付**：[BUG-13](BUG-13-身份验证安全协议.md)；先提交威胁模型 + 协议迁移决策，再修改 Core/Session/Transport；旧服务端和新客户端的兼容或显式拒绝由协议评审决定。

**生产证据：** `src/Session/Networking.cs::PublicWorld` 只清理 `Transactions/CredentialId/CredentialHash/IssuedUidRanges` 及他人 `Uids`，没有移除他人的 `PlayerSnapshot.NativeJson`；`welcome` 收到后会遍历 `World.Players` 调用 `bridge.ApplyPlayer(player.Snapshot, false)`。`src/Session/Authority.cs::SendMapView` 还会按访客/地图所有者，或特定路径的所有玩家，捕获 `PlayerFieldState`。**直接置空他人 Snapshot 可能破坏地表/舰队呈现。**

- [ ] **列出字段投影表**：`welcome`、`playerJoined`、`MapView.Players`、`personalReset`、`galaxy` 分别按收件人标记公开身份/舰队外观、必要现场实体、仅房主与本人可见的个人资金/科技/任务/私人物资。原生 `NativeJson/NativeFieldsJson` 须拆解审计实际内容，不能把 JSON 透明载体默认视为安全。

### P2 量化验收与防回退

- **同条件对比**：固定人数、运行目标、星系/地块、建筑与人员数量、消息频率、运行时长和网络条件；记下两个不同版本的 Git 来源、`BUILD-INFO.json.SourceRevision` 和观测窗口。三目标按真实 DLL 分别构建，**不要求三端 DLL 哈希相同**。

- **UI 主状态**：`未连接 / 认证中 / 房间已就绪 / 地图同步中 / 命令等待房主 / 已应用未保存 / 已保存 / 可恢复失败 / 必须停机保护`；每个界面状态映射到真实会话事件/水位，禁止直接以 `Send()` 成功设置“已保存”。
