## 01 / 为什么这次只选“实测最高收益”的改动

目前并不是没有优化代码，而是缺**可以证明收益的真实游戏数据**。最新已读取源码中的关键实现：

| 链路 | 已有真实实现 | 下一轮待验证的成本与风险 |
| --- | --- | --- |
| **2D 地表捕获** | `src/Game/NativeMapReplicator.cs` 的 `CaptureUpdate` 处理实体集合、原生字段、完整 `string[,]` 格子比较、角色/动物/怪物位姿和个人进度；只有格子变化才克隆格子基线 | 全集合扫描和 `NativeWire.CaptureValue`、全格子比较、每角色属性读取哪个最费主线程时间？缺新版分环节 P95 和对象量 |
| **网络与地图进入** | `Session/MultiplayerSession.Tick` 有事务间的主线程接收预算；`MapViewLoading`、`MapSnapshotCache` 已有可靠 FIFO、地图 ready 屏障、typed `NetworkView` 和 SHA256 缓存验证 | 一条很大的可靠事务仍可能耗时很久；不能用减小每帧预算或拆半条原生事务假装修复 |
| **舰队运动** | `Game/NativeGalaxy.TickPlayerFleets` 只由权威流程调用原生运动；离线舰队与舰战锁状态会冻结；`Session/Commands` 由房主执行用户命令并保留结果 | 客人“已发送/已确认”不等于实际运动；需要双方同一 `CommandId` 和房主物理位移取证 |
| **网络/银河差量** | 现有舰队静态字段与位姿分离、按接收者发送基线、广播共用编码；`SessionPerformance` 提供有界耗时桶、队列与地图块字节量 | 是否仍有重复对象捕获、过大消息、过长队列等待？当前没有新版同场测量 |
| **保存** | `Storage.cs` 和 `MultiplayerSession.SaveOrThrow` 已使用完整保存代和原子提交边界 | 性能提升不能牺牲上一完整代恢复、ACK 与战果幂等 |

## 03 / 具体实验：如何决定先优化哪一行代码

| 实测现象 | 首先定位的调用 | 批准修改前需排除的问题 |
| --- | --- | --- |
| `ground.capture.entities` P95 高，`entitiesScanned` 很多而 `entityChanges` 很少 | `Collections` 中的集合复制、`EntityKey`、`NativeWire.CaptureValue` 和前后基线查找 | 是否包含必需的任务、所有权、伤害或库存更新？不能按“没移动”判断无内容变更 |
| `ground.capture.tiles` P95 高，`tilesScanned` 大但 `tileChanges` 少 | `current.starSpread.getTiles()` 和当前二维全格扫描 | 不能在原生游戏存在未知改格入口时把全扫改成只看已登记脏格；需先对照全量真值 |
| `ground.capture.poses` P95 高，画面频繁跳动 | `hero.transform.localPosition`、`mod_Move`、`roleAnim`、接收者表现插值 | 本地原生动画/碰撞/AI 与远端展示不是同一权威；不能让客端代理参与真正运动与攻击 |
| `transport.handle` 大但 `transport.decode` 不大 | `Networking.Dispatch/ReceiveMapView` 与原生地图恢复操作 | 曾出现小消息触发多秒业务处理；别把慢全部归于网络带宽 |
| 发送成功且房主已接受，却无航行 | `TickPlayerFleets` 中 `localMotionTick`、`getMoveBean().logic()` 及客端 `ApplyGalaxy` | 是房主真的没位移、离线/舰战合法冻结，还是客端远端投影没刷新？缺日志不下结论 |
| `world.save` P95 高 | `SaveOrThrow` 中 Native 捕获与 `Core/Storage` 完整代写入 | 不可拆分未确认事务、取消原子文件替换，或直接返回假保存成功 |

### 统一计量口径

每次实验记录 `WorldId` 的匿名别名、构建指纹、运行平台、2/3/4 人数、地图格子数、实体数、玩家操作步骤、冷/热缓存、网络通道；**不收集真实凭证、聊天内容或玩家存档正文**。一组至少三轮，并分开报告房主与客端的时间桶。`[slow-operation]` 是阈值日志，不能直接换算 P95；`[ground-counts]` 是扫描和变动次数，不能当作实际网络字节。必要时新增固定白名单阶段和限频摘要，禁止逐角色/逐帧无界日志。

目标建议值：**选中热点同条件 P95 减少 ≥25%；其它关键 P95 恶化不超过 10%；零新增资产、ACK、地图修订或完整代存档错误。** 此为未来的验收线，不是对当前代码的成绩断言。

## 04 / 两人到四人的完整回归矩阵

| 验收场景 | 预期保持的 V1 规则 | 阻断情形 |
| --- | --- | --- |
| 房主新建、继续、客人加入/重连 | 联机档与单机档隔离；不同 `WorldId+PlayerId` 的舰队/雇员/资金独立，首次资产只给一次 | 重复生成雇员/母舰、单机档串用 |
| 舰队同星系/跨星系移动及暂停/舰战锁 | 房主唯一推进航行，客人仅提交自己的意图；离线原地冻结、不耗油 | 命令无回执、位置不同步、重复舰队 |
| 冷图、热图、损坏缓存、加载中离开 | 地形 SEED + 所有人物、建筑、库存与真实角色投影完整；加载 ready 后有序重放 | 半张地图、遗漏实体、任期/修订错误、队列卡死 |
| 同一 2D 地图多人工作与关系切换 | 一个有效模拟者；友好工作、中立禁操作、敌对战斗；访客雇员 UID 和归属不变 | 双份生产、跨玩家取物、原版动画/伤害被客户端重模拟 |
| 运输/舰战/离线袭击/战利品 | 一次性事务；离线袭击 10 分钟、结束冷却 60 分钟；一仓上限一次撤离 | 多次撤离、复制资源/伤亡、玩家舰队资产复制 |
| 房主保存、退出、强杀/重开 | 完整 `SaveGeneration` 和上个完整代恢复、错误不伪装成功 | 写入半代、ACK 错配、恢复资产缺失 |

静态构建成功不等于游戏中能加载。真正安装必须使用主仓库的正式构建与同步入口、明确目标已关闭、只替换 `mods/FreeWorldMultiplayer` 分发内容，保留存档与共享 Harmony；未完成人工游戏验收不得把 `RuntimeTested` 写成成功。
