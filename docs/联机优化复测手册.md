# 联机优化复测手册（S0/S1）

> 2026-10-16。这里的日志用于复现与定位，不代表故障已经修好。当前基线 V1.19，后续以游戏内实际加载的 MOD 发布号及包内 SourceRevision 为准。

## 开启、关闭

- 舰队命令诊断：在有真实原生航行操作或命令回执时输出 `[FreeWorldMultiplayer][fleet-command]`，每进程每分钟最多 192 条。没有逐帧日志，不包含昵称、身份凭证、聊天、位置坐标或命令 payload。
- 性能聚合默认关闭：启动游戏时带 `-fwm-profile` 参数，或在**启动游戏进程前**设置环境变量 `FWM_PROFILE=1`。每 30 秒输出一次 `[FreeWorldMultiplayer][profile]`；不需要修改世界存档或联机协议。关闭参数/变量并重启游戏即关闭。
- 新的 2D 地表捕获探针沿用相同开关、约 30 秒的汇总周期。在 `CaptureUpdate` 下一次成功执行时输出 `ground.capture.entities/fields/tiles/poses/personal/total` 的分段耗时窗口，以及 `[ground-counts]` 中的实体、格子和位姿**扫描数量与实际变化数量**；不逐单位记录日志。主线程业务时间和渲染帧耗时不同，且单条大事务仍不可截断。
- 地图新增 `map.cache.encode`、`map.cache.reassemble`、`map.cache.apply` 三个独立耗时阶段；`map.cache.chunks` 汇总的 `fullContentBytes/changedContentBytes` **不包含** JSON/Base64 协议开销，不能当作精确上行/下行网络流量。
- Steam 可在游戏的启动选项中填写 `-fwm-profile`；IP 直连可在真正启动游戏进程之前设置 `FWM_PROFILE=1`。**这只是启用诊断，不会替代原生游戏及 MOD 的实际加载或联机连接。**
- 参考游戏运行时日志：`%LOCALAPPDATA%\CatStudio\FreeWorldMultiplayer\Logs\Steam`、`...\TapTap`、`...\Project3`；收集双方**同一轮**日志时记录 MOD 发布号和 SourceRevision。不要公开个人凭证、原始存档和房间恢复码。

## S0：舰队无法移动的取证

1. 双端进入同一房间，先确定谁是房主。分别从客人和房主本地对**自己**的舰队发送移动命令；注明是否已暂停、舰战是否锁定，以及地图/星系是否相同。
2. 用同一个 `command=...` 在两份日志中找阶段（顺序按具体网络情况）：`native.hook`（此时还没有命令 ID）→ `native.route` → `session.submit` → `client.sent` → `host.received` → `host.native.begin` → `host.native.end` → `host.result` → `client.result` → `native.callback`。
3. 如果连 `native.hook` 都没有，先查原版输入入口或被其他插件绕开的 Harmony Hook；仅有 `native.hook` 无 `native.route`，查 Hook 参数解析或归属门禁；有 `client.sent` 无 `host.received`，查传输和会话；有 `host.native.end=accepted` 但不位移，继续核原版运动与银河投影。**"accepted" 仅表示原生接受命令，不表示舰队已经走到目标。**
4. 观察同一次操作是否出现 `session.defer.map`：若地图加载中排队，该命令应该在原生 ready 后重新提交。若出现 `rejected`，结合玩家看到的明确业务拒绝和旁边错误日志，不凭空猜失败原因。
5. 192 条/分钟的上限可能截断后续探针：单独复现一条命令、重启游戏清空时间窗口，再复查。只有同一命令两端数据齐全才能判定具体断点。

## S1：比较实际性能

**固定条件**：相同游戏版本、MOD 构建指纹、地图、人数、设备和网络；房主与客人都开启性能模式。每场景至少做 3 次。

| 场景 | 观察 |
| --- | --- |
| 房主新建或续开，客人首次入房 | `transport.encode` / `decode` / `handle`，错误和成功回执 |
| 客人同星系移动、跨星系航行 | `galaxy.broadcast`、`transport.encode` 与舰队命令链 |
| 冷图进入、热图再次进入、缓存损坏后重进 | `maps.publish`、`inbound.rounds`、加载秒数、是否全量回退 |
| 同图建筑/人员高频操作 | `maps.publish`、`personal.publish`、队列积压及角色归属 |
| 房主保存、退出及客人断线重连 | `world.save`，保存代/ACK 及恢复是否成功 |

性能行中的 `p50UpperMs/p95UpperMs/p99UpperMs` 是 **固定直方桶的上界估计**；`maxMs` 为真实窗口内最大观察值。`queuedEventPeak/queuedBytePeak/reservedBytePeak` 是每主线程接收轮次采样的 TCP/Steam 接收队列峰值，不代表操作系统网络缓存峰值。`notDrainedFrames` 表示本轮未观察到队列清空，可能由于时间预算、收包上限或背压，不可据此单独判定丢包。

对照改动前后的中位数、P95、最大值、入图时间、字节数、正确性回归，不达标就保留日志并撤回具体优化。**没有用户游戏实测前，不报告已经减少了多少卡顿或网络流量。**

## 本地纯逻辑检查

在主仓库执行：

```powershell
dotnet run --project .\tools\OptimizationChecks\OptimizationChecks.csproj -c Release
```

此命令直接引用生产环境的 `PerformanceWindow` 与 `TransportQueue` 源码，检查耗时桶、计数、队列字节、预留容量和 FIFO 终止事件。它不启动 Unity，也不包含玩家资产或跨机回归；三端正式编译与游戏内验收仍需另外记录。

当前还会同时测试生产 `MapSnapshotDeltaCodec`：大地图分块、冷/热缓存恢复、错误世界、缓存丢失和坏块拒绝。逻辑测试通过**不等于** Unity 原生地图应用测试；应额外复测多人地块内人物、建筑、物资、地图 ready、加载中离开以及重连。
