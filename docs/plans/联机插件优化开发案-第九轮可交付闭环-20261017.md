## 3. 两类实验的具体判定

### A / 舰队：要证明“命令、房主运动、客端表现”三件事

使用现有 `[fleet-command]` 事件与 `tools/Analyze-MultiplayerDiagnostics.ps1`；每一条用相同 `CommandId` 对照两侧。如果日志显示 `host.motion outcome=position-changed`，只说明**房主发生过真实位置变化**，还需现场观察客端投影；`unchanged-after-120-host-ticks` 只是 120 次有效房主采样未见位移，**不是 120 秒，也不是必然 BUG**。任何 `observer-unavailable`、日志版本不匹配或缺 `SourceRevision` 都应报告“证据不足”，不能猜测传输失败。

### B / 2D：先看哪个 CPU 环节真的慢

| 实测阶段 | 优先检查的调用 | 不可破坏 |
| --- | --- | --- |
| `ground.capture.entities/fields` | `CaptureUpdate` 的实体迭代、`NativeWire.CaptureValue` 与确认基线 | 实体 UID、库存、任务、伤害、归属 |
| `ground.capture.tiles` | `starSpread.getTiles()`、`string[,]` 全图比较 | 不能因为格子“通常没变”就跳过未知原生修改；SEED 不能取代人员与物资 |
| `ground.capture.poses` | 原生人物/动物位姿、动画、目标读取 | 客端只展示已确认模拟结果，不多运行一份地表 AI |
| `map.cache.reassemble/apply` | 缓存内容块与 `ReceiveMapView` / `IsMapReady` | FIFO、SHA256、加载屏障、`AuthorityEpoch + Revision`、坏缓存回全量 |
| `transport.handle / galaxy.broadcast / world.save` | 接收事务、舰队按接收者差量、`SaveOrThrow` | 不拆半个原生事务、不丢 ACK、不混用不同 `SaveGeneration` |

对照使用 [第八轮双端性能说明](../guides/联机第八轮性能实测使用说明.md) 和 [六轮 JSON 模板](../联机第八轮双端性能对照模板.json)。`Compare-MultiplayerPerformance.ps1` 按 `histV=1` 的桶计数合并 P95，**不能平均窗口 P95**。合成测试曾通过只是工具检查，不代表游戏加速 25%。不允许为了指标把可靠队列调成丢包、提高上限伪装性能提升，或省略原版模拟。
