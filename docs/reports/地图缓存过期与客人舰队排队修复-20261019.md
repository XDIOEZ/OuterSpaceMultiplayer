# 地图缓存过期与客人舰队排队修复（V1.45）

## 证据与结论

用户报告“地图缓存清单对应的访问请求已过期”，同时客人的舰队无法移动。

本次读取的独立双端日志均为 V1.39，Steam 为房主、TapTap 为客人。客端日志 `20261019-074843.184Z-pid22920-709eec88aaf94de6a133144b1feeceff.log` 在 07:51:06Z 仍有 maps.publish，07:51:07Z 切回星系；07:51:16Z 起点击经过 native.hook → native.route → session.submit → session.defer.map，持续排队，没有对应 client.sent。因此已确认卡在地图同步屏障，尚未进入房主原生舰队移动。日志原件保存在 artifacts/guest-map-cache-fleet-20261019/evidence。

现有日志未找到精确过期文案，不能把下面静态可达分支直接宣布为本次唯一运行根因：房主发出 query 时已授权并保留完整视图；客端插入精确 ViewId 的可靠 FIFO 占位。玩家随后切走旧图会退出 Visitors，迟到的 offer 却再次要求当前 Visitors，从而被拒；普通 error 不填占位，客端在原有60秒期限内阻塞后续地图、个人事务及舰队命令，最终失败关闭。

独立审查未发现另一处确定的离图初始化永久等待：离图前 publish 说明原屏障已解除；原生离图隐藏地图，并不使地图就绪判定依赖可见性。不能为恢复舰队而清空可靠队列。

## 修改

- MapSnapshotCache.cs：仍严格要求已认证玩家、世界、精确 ViewId、地图及既有 pending；履行此前已授权的快照，不以新的 Visitors 状态拒绝历史内容。已发送同玩家同世界同地图同请求的重复 offer 幂等返回；真正失效提示说明原因，不输出身份凭证。
- MapCacheExpiry.cs：等待30秒时仅尝试一次完整地形/完整检查点回填原 ViewId，保持原 FIFO 位置；不调用网络地形准备，不假设任何缓存命中。运输入队失败保留原预算直至原60秒收口，不每帧重发。完整地形允许房主安全升级，仍禁止所需完整地形降级；哈希、任期、修订、个人基线及房主模拟权校验保留。
- FleetCommandTrace.cs：排队事件补充 nativeInit、cacheWaiting、queuedMessages、resyncWaiting、failed，沿用既有每分钟限频和日志异常隔离。

未修改游戏本体、原生舰队航行、资产归属、协议或存档格式。Commands/NativeGalaxy/MapViewLoading 原有未提交差异保留，不吞入本提交。

## 交付与用户验收

本轮不编译、测试、启动游戏或安装。源码为V1.45；当前Steam/TapTap所查日志与安装包仍为V1.39，不能代表本轮源码已运行。后续统一构建安装需双方一起更新，包含此前尚未安装的协议8等改动。

1. 双方更新后，客人由地表回到太空，移动自己的舰队，确认命令到达 client.sent 和 host.received 并实际航行。
2. 快速切换地图/返回太空，确认不再出现旧访问清单误拒、不被历史视图拉回旧地图，个人资产与模拟权保持正确。
3. 缓存协商延迟时确认完整地图回填后恢复；若仍排队，保留同次双端日志，新增 map-state 可分辨具体等待项。

不得把本轮源码修复等同于已通过跨机运行验收。60秒内完整内容仍无法交付时继续失败关闭，不能绕过事务等待继续模拟。
