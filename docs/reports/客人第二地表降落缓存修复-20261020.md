# 客人后降落到不同地表时的缓存暂停

## 报告范围

- 用户复现：房主先降落地表 A，客人随后降落另一张地表 B，客人出现 `Native delta cache revision is unavailable; require a complete acknowledged checkpoint.`，联机暂停无法继续。
- 仅修改联机 MOD；保留原有未提交内容。Project3 / Steam / TapTap 默认只构建打包，不安装、不覆盖运行副本；不启动游戏、不代跑测试或跨机验收。
- 用户追加：增加后续排障所需 Debug，记录地图、修订号、加载、冻结与确认阶段，避免每帧刷屏及身份密钥泄漏。

## 证据与判断

- 实际 Steam 日志 `20261020-094435.413Z-pid207776-cc851ab4375f409283d57172ec722c95.log:13239-13245`，2026-10-20 18:34:08 +08:00：`stage=maps.publish role=guest map=1000000011081 epoch=1 revision=335 paused=True mapLoading=False mapInFlight=0`，异常来自 `NativeMapReplicator.CaptureUpdate`，继而经过 `PublishLocalMapsCore` / `Tick`。
- 这证明失败发生于客人继续捕获地图差量时；当时加载屏障已经解除。当前旧日志没有缓存失效原因与修订号变化记录，不能据此证明当次清缓存的具体调用。
- 静态链路发现：捕获差量 r→r+1 时 Native 已保存 r+1 缓存，Session 仍等待房主确认；运输检查点临时冻结传入已确认的 r，旧 `SetRevision` 将 r+1 缓存删除；真实 ACK 后 Session 保留 r+1 轻量标记，再捕获时缺少对应完整缓存，触发同一保护性错误。
- `ApplyPolicy` 不调用 `SetMapAuthority`，同任期也保留本机已确认修订号；不能将政策广播直接认作清缓存原因。所有缓存按地图 ID 隔离，两人不同地图也可能在运输与全局收口阶段触发上述链路。

## 修复约束

- 只在同一模拟任期、Native 缓存确实处于已确认版本下一代时，保留等待确认的原缓存及 Native 修订号；不伪造 ACK，不直接修改 Session 的确认水位。
- 新任期、恢复完整检查点、外部差量应用仍应丢弃旧缓存；缺少安全基线时仍保留现场并报告，不以强制恢复运行掩盖不一致。
- Debug 应覆盖缓存建立、清理、保留、失配，地图加载与检查点协商，关键 ACK 拒绝及临时冻结/恢复；不记录完整地图 JSON、凭证、房间密钥。

## 用户验收

1. 使用同版本 MOD，房主先进入地表 A，客人随后进入不同地表 B，等待双方完成运输和落地后操作各自雇员。
2. 在运输/空投进行时维持地图活动，检查运输落仓、临时冻结、恢复后的差量是否继续提交；重复切换地表后再试。
3. 如再次暂停，保留双方本次日志，关注 `native-map-cache`、`surface-map`、`session-fault`。不得把新日志存在或包构建成功当作联机已经通过。
4. 当前已经因异常暂停的旧进程不在本次改码中热恢复；更新包后重新开房，从最近完整联机存档复测。
